## 优先修复

### F01 / P1：共享挂载暴露有效后台密钥，部署目录还可被其他容器写入

位置：Ubuntu `/data/docker/DPanel-data/JavSP-Comments/`；本地部署记录 `comments-service/docs/deployment.md:11`，忽略规则 `comments-service/.gitignore:1`。

已确认：

- `pre-cloudflare-20261012.tar.gz` 权限 `0666`，内部包含 `.env`；其中 `ADMIN_TOKEN` 与当前正在使用的后台访问密钥完全相同。还含旧 `GITHUB_TOKEN`，其是否已撤销未验证。
- 服务目录和其父目录 `DPanel-data` 权限及默认 ACL 均允许其他用户读写/穿越，服务目录没有 sticky bit。
- 宿主机 `/data/docker` 的 `0710` 和 ACL 阻止普通本机用户直接穿越，但 `music-tag-web`、`telegram-depiler`、`music-dl` 直接挂载其下的 `DPanel-data`，绕过这个父目录限制。
- 在 `music-tag-web` 中以 **UID/GID 65534:65534** 执行只读权限检查，得到 `BACKUP_READABLE_BY_NOBODY` 和 `SERVICE_DIRECTORY_WRITABLE_BY_NOBODY`。

影响：这些相邻应用发生任意文件读取或代码执行漏洞时，可取得评论后台管理权。目录可写还允许替换源码、Compose 或 `.env`，在后续构建/重启时生效。没有声称这些相邻应用已经被攻破。

建议：移除其他容器对整个 `DPanel-data` 的挂载，分别挂载各应用自己的目录；收紧评论目录、文件和默认 ACL；备份放入独立私有目录，设为 `0600`。完成隔离后轮换后台 `ADMIN_TOKEN`，核查并撤销不再使用的 GitHub 令牌。当前 `.gitignore` 没有覆盖 `.env.*` 和这些备份压缩包，应补充规则。不要直接轮换 `IDENTITY_SECRET`，它关联现有评论身份凭据，需要迁移方案。

### F02 / P1：主应用会话绑定用户名，改密不失效，账号重建会继承新权限

位置：`javsp_web/auth.py:16`、`javsp_web/auth.py:37`、`javsp_web/storage.py:186`。

会话保存 `(username, expires_at)`，每次请求用用户名重新查用户。密码变更没有撤销会话，删除用户也没有清理其会话。

隔离复现：操作员登录后修改密码，旧 cookie 仍有效；删除该用户，再以同名创建管理员，旧 cookie 被识别为 `admin`。旧会话最长 12 小时。线上认证模块与本地完全一致；主应用线上账号变更接口未作写入测试。

建议：用户使用不可复用的内部 ID；会话保存用户 ID 和凭据版本；改密、删除/重建、敏感权限变更时撤销相关会话。检查 Cookie 和 WebSocket 共用认证路径。

### F03 / P1：主应用普通操作员可读取完整敏感配置

位置：`javsp_web/server.py:954`；相同问题还涉及 `javsp_web/server.py:595` 和 `javsp_web/server.py:771`。

`GET /api/config` 仅要求 `current_user`，直接返回原始 YAML 和解析值；`GET /api/presets` 同样面向普通用户，返回完整 `content`、`form`、`form_values`，没有敏感字段过滤。修改配置却要求管理员，形成读写权限不一致。

隔离复现：以 `operator` 身份调用实际提取的 HTTP 处理函数，返回 200，并包含测试配置中的代理密码。真实配置一旦包含代理认证、站点 Cookie、翻译 API key 等，普通账号即可读取。未使用生产配置进行泄露测试；此项为本地当前代码确认。

建议：管理员专属配置读取；普通用户仅获得任务所需、按字段白名单构建的配置摘要。需要同时处理 YAML 原文和多个派生字段，单纯隐藏页面按钮不足以修复。

## 评论与后台滥用

### F04 / P2：公开读取没有应用级限流或缓存，会持续消耗 Worker/D1 配额

位置：`comments-service/worker/src/index.js:7`、`:124`、`:125`、`:157`。

匿名评论列表、配置和健康检查均直接访问 D1，统一响应 `Cache-Control: no-store`，没有读取限流。构造不存在的番号也可触发数据库读取。

本地复现：同 IP 匿名读取 150 次全部 200，对有评论的番号产生 300 次数据库调用，没有读限流记录。免费额度耗尽可导致正常读写不可用。此结果没有证明生产 WAF 完全不限流；本次未导出 Cloudflare 边缘规则。

建议：在触发 D1 前实施边缘读取限流和全局预算；缓存公开列表/配置，将个性化 `liked` 状态与公共响应分开，避免把用户状态跨账号缓存；健康检查不必每次查询主库。不能只用额外 D1 写入承担所有恶意请求的限流工作。

### F05 / P2：评论和点赞额度只有 IP 维度，换 IP 可绕过同一身份限制

位置：`comments-service/worker/src/index.js:145`、`:169`。

已登录身份没有独立的写入频率或每日预算；`limit()` 默认按 `CF-Connecting-IP` 的 HMAC 计数。

本地复现：同一真实模拟会话，12 个来源 IP 连续提交 12 条评论，全部 201。既绕过同一身份 30 秒冷却，也超过通常理解的每小时 10 条额度。真实攻击仍需每次通过 Turnstile，不能直接伪造 Cloudflare 写入的来源头；代理池/分布式来源是必要前提。

建议：同时设置 IP、已认证身份及全局额度；保留数据库原子准入。点赞已有 `(comment_id, author_hash)` 唯一键，所以此项不会让同一身份对同一评论重复计赞。

### F06 / P2：举报无上限展开，能够破坏后台审核列表

位置：`comments-service/worker/src/moderation.js:79`、`comments-service/admin_proxy.py:36`。

后台评论虽然每页最多 50 条，但每条评论的未处理举报全部返回。举报仅按 IP 去重，能随不同来源无限增长。代理只读取前 1,048,576 字节，却继续以成功 JSON 响应返回截断内容。

本地复现：一条评论附带 1,500 条合成举报，每条理由 300 个汉字，列表响应 **1,393,771 字节**，超过代理上限。截断后 JSON 不完整，前端拿不到 `items`，该页审核失效。需要大量有效举报，真实请求仍受每 IP 额度和 Turnstile 约束。

建议：列表只返回举报计数和有限样本，举报详情独立分页；限制单条评论的未解决举报存储量/合并重复内容；代理对超长响应返回明确错误，不静默截断成功响应。

### F07 / P2：按用户名共享硬性限额，可定向锁住身份登录/注册

位置：`comments-service/worker/src/identity.js:43`。

同名不同 PIN 本来是不同身份，但配额只按用户名计数，且在验证凭据之前消耗。攻击者知道公开名中的用户名即可影响该用户名下所有身份。

本地复现：30 次错误 PIN 请求（不同合成 IP、模拟通过 Turnstile）之后，新来源的同名注册收到 429。已有有效会话不受此登录限额影响；真实攻击需要足够来源和有效挑战。

建议：保留防爆破约束，同时把注册与登录分开，采用完整身份标识、递增退避和风险控制，避免让可廉价消耗的公共用户名额度成为长时间硬锁。不要简单删除账号维度防护。

### F08 / P2：评论身份会话长达 90 天，缺少撤销和凭据更换路径

位置：`comments-service/worker/src/identity.js:16`、`:71`；`javsp_web/storage.py:168`。

每次登录产生新会话，旧会话继续有效。没有会话注销、注销其他设备、PIN 更换、管理员撤销身份会话的 API；定时任务只清理过期令牌。主应用登出只撤销主应用 Cookie，不撤销 Worker 令牌。

影响：会话从共享主应用部署、浏览器脚本或数据备份泄露后，可以持续读取该身份待审核/隐藏历史、冒名评论和点赞，受害者无法自行撤销。D1 保存的是摘要，这是正确做法，但不能替代撤销机制。

建议：提供会话撤销和所有设备退出、凭据版本/失效时间及安全的 PIN 更换流程，缩短高风险会话寿命。主应用本地缓存该令牌属于当前设计的信任边界，部署者能够读取它，应明确告知用户。

### F09 / P2：管理后台接受明文 HTTP 管理凭据

位置：`comments-service/compose.yaml:6`、`comments-service/admin_proxy.py:65`、`comments-service/static/admin.js:6`。

线上绑定 `0.0.0.0:8095`；`http://127.0.0.1:8095/admin` 返回 200，无 HTTPS 重定向；在该 HTTP 入口携带真实管理密钥读取统计也返回 200。页面直接在 Authorization 头中发送长期后台密钥。

本次从当前电脑直接连接 `x.apecme.com:8095` 失败，因此**未确认此端口可以被任意公网客户端访问**。风险在于通过可达局域网/转发端口直接 HTTP 登录时，凭据可被链路观察者截获；SSH 隧道或正确的 HTTPS 代理可避免此问题。

建议：后台仅绑定回环，明确通过 SSH 隧道或 HTTPS 反向代理访问；防火墙阻断绕过 HTTPS 的直接入口。仅添加 CORS 不会加密或保护这个凭据。

## 主应用补充问题

### F10 / P2：登录接口缺少尝试限流，且会话 Cookie 没有 Secure

位置：`javsp_web/server.py:490`、`:495`。

隔离测试 25 次连续错误密码全部 401，未出现 429 或退避；每次有效用户名尝试都执行 240,000 轮 PBKDF2，可被用于猜测弱口令或耗尽 CPU。成功登录的 Set-Cookie 没有 `Secure`，即使部署正常走 HTTPS，也可能在可达 HTTP 同域请求中携带 Cookie。

建议：在昂贵密码校验前做来源和账号维度限流；HTTPS 部署设置 Secure，并正确处理可信反向代理。不要无条件信任客户端传入的 `X-Forwarded-For/Proto`。

## 设计风险与已验证防护

- 六位 PIN 只有一百万种组合，允许 `123456` 等常见值；同用户名、同 PIN 的重复“创建”直接返回已有身份的新会话，四位公开后缀不是额外认证因素。此行为符合现有设计而非新发现的校验绕过，但两个用户选中相同凭据会共享身份，建议使用更强凭据或明确接受这一风险。不要把 HMAC 存储等同于凭据本身具有高熵。
- 新安装会创建 `admin/admin` 且不强制改密。**当前 Ubuntu 主应用已验证不再使用这一默认密码**，不将新安装风险误报为当前生产弱口令。
- 后台浏览器密钥与 Worker 管理密钥独立，均为 64 字符；代理只在服务器端添加 Worker 密钥，拒绝上游重定向，管理页面不使用 localStorage 保存密钥。
- 管理接口先鉴权，普通公开请求不返回作者摘要、删除凭据摘要或私有会话表；敏感主应用 profile 只面向当前登录用户，并使用 no-store。
- SQL 值使用绑定参数，动态排序字段白名单；本次未发现可利用的 SQL 注入或未认证管理接口绕过。
- 评论、用户名、举报原因在前端输出时转义；管理代理有 CSP 和 frame-ancestors 限制。本次未发现评论导致的存储型 XSS。
- Turnstile 服务端验证 success、hostname、action，缺少密钥时关闭写入；验证消息接收端检查 origin、source、nonce、action。通用跨域公开接口是支持独立部署的设计，不直接构成 Cookie 型 CSRF。
- 单条评论长度、JSON 请求体大小、分页大小有上限；写限流的 D1 条件更新是原子的。相同身份同一评论点赞有唯一约束。
- Ubuntu `/.env` 和 `/static/../.env` 均返回 404；不是通过评论后台静态路由直接下载到密钥。风险 F01 来自共享文件系统。

- 已有 Worker 测试 **17/17**、代理测试 **5/5**、评论与社区前端测试 **7/7**，合计 **29/29** 通过。测试通过不覆盖本报告新增的攻击场景。

## 建议顺序

1. 先处理 F01：隔离挂载、收紧权限/默认 ACL、私有保存备份，随后轮换后台密钥和处理旧 GitHub 令牌。
2. 修复主应用 F02/F03，清理旧会话，检查普通用户曾可读取的敏感配置是否需要轮换。
3. 修复 F06 以保障举报审核入口可用，再补充公开读取、身份/IP 双维度额度和定向锁定防护。
4. 加入身份会话撤销，完成 HTTPS/登录保护，并把本报告复现转为回归测试后再部署。

本报告不建议仅提高代理读取上限、仅增加前端按钮限制或仅关闭 CORS；这些做法不能解决对应根因。
