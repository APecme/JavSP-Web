## 5. 必须记录的已知缺陷：ASSET_VERSION 仍是旧值

`server.py:105` 在**进程导入时**计算：

```python
ASSET_VERSION = hashlib.sha256(b''.join(...(WEB_DIR / 'assets').iterdir()...)).hexdigest()[:16]
```

当前子进程 16:06:04 启动 → 内存里的 `ASSET_VERSION = 721d329cbde33cb3`；按新资源重算应为
`67b569445a83c814`。`server.py:126` 只在 `?v` 等于 `ASSET_VERSION` 时下发
`public, max-age=31536000, immutable`，实测 `/assets/app.js?v=721d329cbde33cb3` 确实是
`immutable`。

后果：16:06–16:24 之间打开过页面的浏览器，已经在 `?v=721d329cbde33cb3` 这个 URL 下缓存了
旧的 `app.js` / `navigation.css` / `page-layouts.css`，在版本号变化前**不会回源**。也就是说
文件已上线，但这类浏览器可能仍显示旧界面，硬刷新（Ctrl/Cmd+Shift+R）或重启子进程才能看到。

修复方式：重启 `apps/1.1.42` 子进程使 `ASSET_VERSION` 重算（沿用
`docs/reports/multipart-copy-20261023/restart-20261023.py` 的通道切换路径；重启会清空内存会话，
浏览器需重新登录）。当前队列活跃任务 0（`tasks.db` 查询），重启不会因 updater 的
`active_tasks()` 保护被拒。本次**未执行**重启，等 apecme 确认。

## 追加：不去重启的缓存绕过（16:35 CST）

用户反馈「看到的还是旧界面」。实测：`/` 返回的 HTML 已是新版（热片/下片在前），但 `ASSET_VERSION` 仍是进程启动时算出的旧值 `721d329cbde33cb3`，因此 HTML 里的 `?v=721d…` 命中浏览器 `immutable` 缓存，CSS/JS 全是 16:06 之前的。

改法（不动进程、不掉登录态）：把 overlay 里 `index.html`、`login.html` 的资源 URL 从 `?v=__ASSET_VERSION__` 硬编码成当前真实哈希 `67b569445a83c814`（即重启后会算出的值）。`/` 与 `/login` 都是请求时读文件且 `no-store`/`no-cache`，所以刷新即生效。

- 备份：`/data/docker/DPanel-data/javsp-web/data/updates/backup-20261023-163506-asset-version-bust/`
- 实测：`/` 输出 `?v=67b569445a83c814`；`/assets/navigation.css|app.js?v=67b569…` 的 sha256 与工作区**完全一致**；响应头 `Cache-Control: public, no-cache`（因为内存里的 `ASSET_VERSION` 仍是旧值，不匹配就不会下发 immutable）。
- 代价与后续：overlay `index.html`/`login.html` 与工作区仅差这个查询串，**下次重启后** `ASSET_VERSION` 会重算成 `67b569445a83c814`，需把这两个文件恢复成工作区版本（`cp` 或重新同步）。长期解法是让 `server.py:105` 的 `ASSET_VERSION` 按 assets 目录 mtime 惰性重算，避免每次改前端都要重启。
- 回滚：把备份目录的 `index.html`、`login.html` 拷回 overlay 即可（缓存会退回到旧不可变 URL 的状态）。
