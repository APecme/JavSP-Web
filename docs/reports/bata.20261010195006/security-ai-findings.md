## 执行摘要

2026-10-11 按目标版本功能复核后，本专项为 **2 项功能缺陷、3 项条件性风险**。功能缺陷为同名账号重建后旧 cookie 可继承新角色（SEC-03 的实验 B）及已承诺的工具结果凭据脱敏不完整（SEC-05）。SEC-01 改列预设共享的凭据信任边界风险；SEC-02、SEC-04 分别要求认证文件损坏和恶意来源 DNS 条件。全部复现证据保留，详见[功能适配复核说明](功能适配复核说明.md)。

这些结论并不等于发现无认证 RCE。自定义 Python 爬虫是管理员明确提供的执行扩展，现有 AI 写入确认也有服务端检查，不能将其简单归类为“提示注入即可任意执行”。

|---|---|---|---|

| SEC-02 | 条件风险 / P1 | `users.json` 损坏被当作首次启动，重建 `admin/admin` 并覆盖账号 | TestClient、临时认证文件损坏复现 |

| SEC-04 | 条件风险 / P2 | 公网 DNS 验证后重新解析，恶意来源可使 AI 资料请求到达内网 | 模拟 DNS 重绑定 + 真实本机 HTTP 连接 |
| SEC-05 | 功能缺陷 / P2 | 已声明的工具结果脱敏遗漏 Bearer 凭据正文及 Cookie | 纯函数合成输入复现，未发生真实凭据泄露 |

## SEC-01：共享预设凭据边界（条件风险 / P2）

**功能复核。** `web/assets/app.js:3363–3364` 对 operator 仅移除系统设置、自动刮削、爬虫配置、AI 刮削导航，保留预设页；`server.py:548–554,907–915` 明确允许已登录用户读取/转换预设，写入则要求管理员。目标 README 没有说明预设中的翻译密钥必须对 operator 隐藏。因此读取 HTTP 200 本身符合已提供的预设查看能力，不能称为绕过管理员读权限。原结论的 P1“配置越权”改为 P2 条件风险；需要区分预设使用权与密钥知情权时再制定并实现脱敏规则。

- 位置：`javsp_web/server.py:548–550`、`:724–751`、`:907–915`。
- 根因：`GET /api/presets` 与兼容接口 `GET /api/config` 仅要求 `current_user`；`_public_preset()` 返回原始 `content`、`form`、`form_text`、`form_values`，没有按用户角色筛选或脱敏。`get_config()` 返回 YAML 原文及解析对象。
- 触发：管理员在全局配置或预设中配置翻译服务 `api_key`、带用户名密码的 `network.proxy_server`；任意有效 operator 登录后直接调用接口。
- 实验：独立临时 data，分别写入 `SYNTHETIC_TRANSLATOR_SECRET` 与 `SYNTHETIC_PROXY_PASSWORD`；两条接口均返回 HTTP 200，响应中同时存在两个合成秘密。这证明预设可见内容包含凭据，不证明读取权限被绕过。
- 影响：若管理员给不应知道这些凭据的账号分配 operator，其可复制付费翻译密钥或代理账号；单管理员/共同信任账号使用时不构成越权。后续风险取决于凭据外部权限。
- 策略建议：若产品决定“操作员可查看非敏感预设，但不能读取凭据”，提供统一安全投影，覆盖 YAML 与嵌套对象；保留操作员选择预设和正常刮削能力。不要仅据报告收回产品已有的预设查看权。
- 策略验收：明确上述隔离目标后，再用真实 operator 会话验证 `/api/presets`、`/api/config` 及转换接口的所有形态均脱敏，同时验证预设查看和启动流程仍可用。

## SEC-02：认证文件损坏触发默认管理员重建（条件风险 / P1）

- 位置：`javsp_web/storage.py:41–45`、`:72–81`、`:152–159`；登录入口 `javsp_web/server.py:486–492`。
- 根因：`_read_json()` 将不存在、JSON 损坏及 I/O 错误统一转换为 fallback。`ensure_seed_data()` 对非列表/空列表一律写入 `admin/admin`。`find_user()` 在认证时调用该初始化函数，因此不仅发生在重启时，下一次登录请求即可触发。
- 触发：已有部署的 `users.json` 被截断、手工编辑成非法 JSON、替换成错误结构或空列表；如果目录允许写入，随后认证请求会恢复已知默认凭据。只读故障不一定能够成功写回，因此不能将所有权限错误都断言为可登录。
- 实验：先修改临时管理员密码，确认 `admin/admin` 登录返回 401；将该临时文件写成截断 JSON；下一次相同登录返回 200，账号文件只剩新建的默认管理员，原用户被覆盖。
- 影响：认证状态由错误进入开放的默认账号状态，同时丢失原账号列表。攻击者不能仅靠普通 HTTP 请求制造文件损坏，因而这是“故障后的认证失守”，不是已证明的远程任意触发重置。
- 修复：区分明确首次初始化与损坏/读取失败；已有实例的认证数据错误必须拒绝认证并保留原文件、报警。引入初始化标记/可恢复备份，初始化密码使用随机一次性值或安装时显式设定，避免固定默认口令恢复路径。
- 回归：非法 JSON、错误结构、空列表、文件缺失、不可读分别验证；既有实例均不得自动创建已知口令。

## SEC-03：同名新账号继承旧会话（功能缺陷 / P2）

**功能复核。** 现有管理员接口按当前角色授权；删除旧 operator 后创建同名 admin，旧 cookie 重新获得新角色，违反这条已经实现的身份/角色边界，因此实验 B 仍计功能缺陷。目标“用户管理”仅承诺修改账号名、密码并要求密码确认，没有说明改密自动退出所有已登录会话；实验 A 单独属于会话撤销策略观察，不把它表述为改密无效。

- 位置：`javsp_web/auth.py:12–19`、`:29–41`；`javsp_web/server.py:528–545`；`javsp_web/storage.py:161–185`。
- 根因：session 只记录 `(username, expires_at)`。密码变更与删除账号没有撤销该用户名的 session；访问被删用户只返回 401，不移除 token。重新创建同名用户后，旧 token 会读取新账号及新角色。
- 实验 A：修改 operator 密码成功，旧密码再次登录返回 401，但原 cookie 的 `/api/auth/me` 仍返回 200。
- 实验 B：删除 operator 后原 cookie 返回 401；以相同用户名创建一个新管理员、赋予不同密码；原 cookie 随即返回 `role=admin`，访问管理员接口 `/api/users` 返回 200。
- 影响：改密码无法隔离已泄露会话；在同名账号重新分配的场景中，原账户持有人可冒用新账户。既有会话最长持续 12 小时，服务重启会清空内存会话；这两个条件限制持续时间，但不能代替撤销。
- 修复：用户记录增加不可复用身份 ID，session 绑定该 ID；删除时撤销关联 token，账户不存在时移除已无效 session，避免同名复用。若增加“改密后退出其他会话”策略，再通过 session_version 或 token 撤销实现，并向用户说明该行为。
- 回归：删除并同名新建后旧 token 不得取得新账号角色。修改密码后旧密码必须不能重新登录（现有实验已通过）；旧会话是否立即失效按明确后的产品策略验收。

## SEC-04：AI 公开网页 SSRF 防护存在 DNS 检查/连接时间差（条件风险 / P2）

- 位置：`javsp_web/ai_scrape.py:40–48`、`:53–61`；同类模式还出现在 `javsp_web/tasks.py:1294–1313`、`:1336–1346`。
- 根因：`_public_target()` 用 `socket.getaddrinfo()` 验证 IP 后，`requests.get()` 仍使用原主机名重新解析，未绑定已验证地址/校验实际对端。对于经代理的请求，本地解析与代理解析也不一定一致。
- 触发：攻击者控制被 AI 搜索并选中的来源域名及 DNS，在检查时返回公网地址、连接时返回私网/回环地址；目标服务需能在允许端口响应。`ai_scrape` 将 URL 端口限制为 80/443，本结论不表示任意端口扫描。
- 实验：`security_dns_repro.py` 只启动临时的 `127.0.0.1:80` 合成 HTTP 服务，模拟解析器对同一域名第一次返回公网 IP、第二次返回回环地址。真实 requests 连接取得 `SYNTHETIC_LOCAL_ONLY_SERVICE_RESPONSE`，服务端记录一次请求。没有访问真实内网服务或真实攻击域名；DNS 变化是模拟的，HTTP 传输是真实的。
- 影响：可对内部 HTTP 服务发起 GET，并将正文作为 AI 来源进入后续提取流程；在正文包含目标番号等筛选信息时，存在把内网内容发送给已配置模型服务的路径。未验证更进一步的数据窃取、状态变更或 RCE。
- 修复：采用能够固定已校验地址并保留正确 Host/TLS SNI 的传输层，逐跳校验实际连接对端；代理模式通过可信出口策略隔离私网目标。Clash Fake-IP 的 `198.18.0.0/15` 兼容需要显式配置，不应把其等同于普通公网地址。
- 回归：实际连接解析变化、重定向、IPv4/IPv6、显式代理、透明代理分别验证。现有私网重定向测试只覆盖 URL 检查，未覆盖该时间差。

## SEC-05：AI 文本脱敏在常见请求头格式下残留凭据（功能缺陷 / P2）

**功能依据。** 目标 README 的 AI 使用说明明确写“工具结果会隐藏凭据”；文本工具结果的常见 Authorization/Cookie 格式未满足此说明。触发前提是工具资料中已经存在凭据，不表示日常爬虫必然泄露，也不是要求模型能识别任意未知秘密。

- 位置：`javsp_web/ai.py:131–143`；发送工具结果给 LLM 的路径为 `javsp_web/ai_router.py:322–328`。`get_crawler` 返回源码、`get_task` 返回日志的工具见 `javsp_web/ai_tools.py:63`、`:156–158`、`:170–172`。
- 根因：字典键的脱敏能隐藏结构化的 `authorization`/`cookie`，但源码、日志和消息属于字符串。字符串正则在空格处停止：`Authorization: Bearer credential` 只隐藏 `Bearer`，真实 credential 留下；字符串规则完全未包含 `cookie`。
- 合成实验：`redact({'source': "headers = {'Authorization': 'Bearer SYNTHETIC_BEARER_CREDENTIAL'}"}, 'different-llm-api-key')` 的结果仍含完整合成凭据；`Cookie: session=SYNTHETIC_COOKIE_CREDENTIAL` 完全保留。结果已写入 `security-redaction-repro-results.json`。
- 影响边界：必须先有凭据出现在自定义源码、工具日志或粘贴文本中，才会触发；内置爬虫目前采用 CookieCloud，未发现其中预置真实认证凭据。已配置 LLM 本身的 API key 还有精确字符串替换，不受这个特定 Bearer 前缀问题影响。此项属于防止意外发送秘密的保护不完整，不能声称已发现真实泄露。
- 修复：对 Authorization/Cookie 请求头按完整字段值移除，对源码/日志入模设置专用清洗；用 Bearer、Basic、Cookie、带引号字典、换行头部与 URL 凭据形成回归用例。业务日志本身应避免输出认证头。

## 已有有效控制与设计边界

1. **AI 写入不是只靠提示词防护。** `/api/ai` 整体 require_admin，对话绑定 owner；创建/修改工具生成 pending action，后端 `execute()` 要求 `confirmed=True`，确认接口拒绝重复执行，部分编辑操作比对 snapshot。重启时 executing 操作标为 unknown，避免盲目重放。尚未证明可绕过这些确认直接触发写工具。
2. **对网页资料有来源约束。** 番号、标题、来源 URL、封面归属有后端核验，搜索关闭也在工具执行前再次检查；支持响应体大小、轮数、工具次数限制。但时间差 SSRF 和较松的部分事实匹配仍应独立处理。
3. **认证基础并非明文密码。** 使用 PBKDF2-HMAC-SHA256、随机 salt、240,000 次迭代和常量时间比较；session token 有足够熵、HttpOnly 与 SameSite=Lax。问题集中在生命周期与初始化，而非哈希算法。
4. **管理员自定义 Python 属于可信代码执行能力。** 保存仅做编译/函数存在检查，测试以当前服务用户的子进程运行，继承环境、配置和 CookieCloud。管理员被攻破即意味着该宿主/容器权限内代码执行。需要最小文件挂载/服务账号权限；若要支持“不可信用户提交爬虫”，必须另加进程/容器隔离，现版本并无该信任边界。
5. **AI 对自定义爬虫的“只读测试”是功能分类，不是操作系统沙箱。** `test_crawler` 在 AI 注册表中标记为非 mutation，模型可自动调用已有爬虫；管理员保存的代码可能产生副作用。建议在产品中明确告知，或为自定义爬虫的首次/版本变更后测试设置独立确认。这一事实不单独计作未授权 RCE。
6. **AI Markdown 输出避免直接 HTML 注入。** 使用 DOM `textContent`，链接协议限制 HTTP(S)、新窗口带 noopener noreferrer；未在该渲染器发现直接 XSS 路径。

## 部署与加固观察（不等同于已利用漏洞）

- Docker 示例把 `8090:8090` 发布在宿主所有接口，服务监听 `0.0.0.0`，首登固定 `admin/admin`；文档要求立即修改，但无强制改密/首次引导。桌面默认 `127.0.0.1` 暴露面较小。不能以本次源码审查断言用户当前实例已暴露公网。
- 登录接口未见失败次数限制/退避。session cookie 未设置 Secure；HTTPS 部署宜结合可信代理设置安全 cookie，并收紧来源。SameSite=Lax 是现有 CSRF 缓解，不应误写成“完全无 CSRF 防护”。
- AI/下载器/媒体服务/CookieCloud 凭据明文存在应用数据目录，适合单机信任边界但需要文件权限、备份权限控制。管理员配置任意 LLM URL、Ollama 或 SearXNG 内网地址本身是支持功能，不能单凭私网 URL 认定权限绕过 SSRF。
- 运行与停止、HTTP 流超时、CookieCloud/爬虫进程最小权限仍应结合真实部署压测；本专项未声称完成互联网渗透测试或生产配置核验。
