## 逐项发现

### T01 / 功能缺陷 / P1：未完成下载的显示进度被用于刮削和移除决策

- **位置**：`javsp_web/qbittorrent.py:97`；`javsp_web/server.py:1501–1504`、`1609–1619`。
- **原因**：下载器原始 `progress` 先 `round(progress * 100, 1)`，自动刮削和自动移除直接判断这个显示值是否达到 100，未使用原始比例或下载完成状态。
- **触发条件**：如原始进度 `0.9996`（99.96%），仍为 `downloading`，显示进度变成 `100.0`。启用匹配的自动刮削规则即可提前派发；自动移除还需开启且满足一项分享阈值。
- **复现**：返回 `state=downloading, progress=0.9996, completion_on=-1` 的假 qB 数据，归一化后为 `100.0`，`_auto_scrape_match=True`；模拟 `ratio_limit=0` 时 `delete_torrent` 被调用。
- **影响**：尚未完成的媒体可能被提前整理；若移动文件，可能中断下载/留下不完整成品。移除接口发送 `deleteFiles=false`，因此本项不是直接删除文件，但可在完成前移除种子、停止其继续下载。
- **建议**：保留 `raw_progress` 和明确的 `is_complete`；将显示用四舍五入限定在 UI 层。派发和移除应依据原始完成比例及适当的完成状态；加 99.94%、99.96%、100%、校验中等边界回归。
- **置信度**：高，真实原函数离线复现。

### T02 / 功能缺陷 / P1：子进程启动前取消，会被 finally 改回 running

- **位置**：`javsp_web/tasks.py:1138–1140`、`1148–1159`、`1167–1169`、`1231–1236`、`1962–1976`；恢复逻辑 `1996–2010`。
- **原因**：工作线程持有任务副本。`cancel_task()` 另读一份记录并保存 `cancelled`；工作线程在 Popen 前发现取消后仅 `return`，随后 `finally` 把旧副本的 `running` 状态重新 upsert，并删除取消标记。
- **触发条件**：任务已进入 running，但仍在 CookieCloud 获取/启动准备阶段，用户点击停止。无需真实子进程已启动。
- **复现**：在 `get_cookiecloud_settings` 注入取消，数据库状态依次为 `cancelled → running`，Popen 确认没有被调用。
- **影响**：UI 上出现没有对应进程的永久 running；再次取消才可能纠正。服务重启还会按 running 恢复并重新排队，违背先前的停止意图。
- **建议**：取消状态和终态更新采用同一受控状态机；Popen 前取消分支显式将当前工作副本终止，并在 finally 读取/比较持久状态或用条件更新禁止覆盖 cancelled。增加“预启动取消”和“取消后重启”测试。
- **置信度**：高，真实任务存储和取消函数复现。

### T03 / 条件风险 / P1：分 P 整理中途失败会留下缺少自动还原清单的部分提交

**功能边界**：分 P 合并整理与成功后的还原是已有功能，但目标说明没有承诺跨多文件的原子事务或任意 I/O 失败时自动回滚。本项的部分移动事实与影响保留，以失败恢复风险验收；它不证明正常分 P 整理失败，也不证明文件字节丢失。

- **位置**：`vendor/JavSP/javsp/datatype.py:196–202`；`vendor/JavSP/javsp/__main__.py:662–666`；`javsp_web/tasks.py:830–835`。
- **原因**：全体目标冲突预检查后，分段顺序移动；任何一次运行时 I/O 失败均不回滚。`self.new_paths` 和 `file_organizer` 事件都要全部移动成功才写出。
- **触发条件**：第一段成功，第二段因挂载断连、权限、磁盘空间等 I/O 失败。预检查只能避免预先已存在目标，不能避免执行阶段失败。
- **复现**：使用两段假视频，第二次 `shutil.move` 注入 OSError。第一段已在输出目录、原路径不存在；第二段仍在输入目录；`new_paths` 不存在。
- **影响**：一部影片分散于输入/输出目录，任务失败且没有 Web 还原所需清单；再次按原 `input_files` 重试还可能因第一段缺失失败。没有直接证据表明媒体字节丢失，但自动恢复保证不足，需要人工找回/搬移。
- **建议**：先持久化完整整理计划，逐步记录提交状态；失败逆序补偿或明确保留可恢复清单。验证移动、硬链接、跨卷、第二段失败和进程中断场景，回滚失败本身也必须可见。
- **置信度**：高，实际假文件移动 + 故障注入复现。

### T04 / 功能缺陷 / P2：默认相对输出路径的还原功能不可用

- **位置**：`vendor/JavSP/config.yml:118`；`vendor/JavSP/javsp/__main__.py:857–860`、`666`；`vendor/JavSP/javsp/datatype.py:195`、`202`；`javsp_web/tasks.py:647–648`、`832–835`。
- **原因**：默认输出规则是 `#整理完成/{actress}/[{num}] {title}`。子进程切到输入目录后生成相对 `new_paths`，事件原样传回；Web 后端却在自己的工作目录下将这些值转换为 Path 并检查文件。
- **触发条件**：保持默认相对输出规则，输入目录与 Web 服务工作目录不同，成功完成媒体整理后点击还原。
- **复现**：子进程等价工作目录内成功整理到相对 `#organized/TEST-002`，回到 Web 工作目录后 `restore_available=True`，`restore_task_files=False`，实际输出文件确实存在。
- **影响**：用户看见可还原入口却不能还原；相对 `generated_files` 也存在同类基准目录歧义。后者未在本次测试中制造同名路径，不据此断言已经误删文件。
- **建议**：在子进程事件边界将 original/organized/generated 全部转为绝对路径；旧记录按记录中的输入根目录或绝对 output 迁移，并验证结果受输出根约束。
- **置信度**：高，默认配置链路和实际假文件复现。

### T05 / 功能缺陷 / P2：图片重试的旧任务快照导致删除复活和已接受编辑丢失

- **位置**：删除 `javsp_web/tasks.py:2027–2036`；后台图片重试 `1890–1939`；资料修改 `809–826`；全量 upsert `javsp_web/task_store.py:24–28`。同模式也见封面搜索最终保存 `tasks.py:1791–1798`。
- **原因**：删除/资料编辑没有与图片重试建立同一任务的互斥或版本条件，后台线程持有旧 dict，并持续全量 upsert。删除只拒绝 running/有主进程的任务，允许 `image_retry_running=True` 的已完成任务。
- **触发条件**：已完成影片开始补图片；下载过程中删除记录或编辑影片资料。
- **复现 A**：删除返回成功、SQLite 当时查无记录，图片重试后记录重新出现。
- **复现 B**：编辑接口接受 `title=User edit`，当时数据库正确；重试结束后 `metadata_override` 消失。
- **影响**：用户删除不持久，编辑静默丢失。主任务、图片重试、封面检索、手工编辑间缺少明确写入所有权。
- **建议**：任务版本号 + CAS 更新或按字段更新；删除使用 tombstone/取消后台操作；拒绝对已删除任务 INSERT。不要只靠全局锁保护每一次写，因为两个旧快照在不同时间依次写仍会覆盖。
- **置信度**：高，两种情形均真实 SQLite 离线复现；封面搜索同类风险仅代码审查，未另运行其子进程链路。

### T06 / 功能缺陷 / P2：下载去重记录限制 1000 条导致旧下载反复重新刮削

- **位置**：`javsp_web/storage.py:372–376`；`javsp_web/server.py:1571–1581`、`1588–1606`。
- **原因**：可展示的历史和防止重复派发的唯一索引是同一 JSON，保存时丢弃前 1000 条以外的旧记录。被淘汰下载若仍在做种/仍匹配，下轮变成“从未刮削”。
- **触发条件**：同一配置累计匹配下载超过 1000，且旧下载仍在列表/路径仍存在（硬链接或不移动原文件场景尤其常见）。
- **复现**：1001 个模拟下载首次创建 1001 个任务，保存后只有 1000 个 key；完全相同列表第二轮又创建 1 个。后续淘汰可继续触发轮转。
- **影响**：重复抓取、写文件、占队列；“每个已完成下载最多刮削一次”的注释语义不成立。
- **建议**：将有界展示历史与持久去重索引分离；下载器 ID + torrent hash 建唯一键。仅在明确允许重新处理或确认下载移除后按策略清理。
- **置信度**：高，使用原保存函数和原派发函数离线复现。

### T07 / 条件风险 / P2：普通任务持全局锁查询挂载封面，拖住无关任务操作

**功能边界**：README 明确允许底层挂载调用等待网络，并说明返回后停止后续处理；不能把无法中断内核 I/O 本身判作取消失败。本项另有具体证据：单个封面 stat 的等待经全局锁传播到无关任务，属于慢挂载条件下的可用性风险，需用真实 NAS 验证时长和影响。

- **位置**：`javsp_web/tasks.py:587–591`、`719–722`、`608–646`、`426–438`、`392–408`；`task_store.py:17–20`。`list_tasks` 同样持锁装饰详情：`tasks.py:594–599`。
- **原因**：`_persist` 持 `_lock` 调用 summary 生成；装饰器解析图片输出时执行 `Path.is_file()`。该 `_lock` 同时是排队条件锁，扫描提交、取消、状态持久化等均共享。
- **触发条件**：任意已有任务的海报/封面位于失联或长时间不响应的挂载盘，恰逢任务写入/详情查询。
- **复现**：仅 mock 对一个任务 `poster.jpg` 的 stat 为阻塞；另一个无需访问媒体的扫描任务 `_persist` 也在等待。释放封面 stat 后两者完成。
- **影响**：该版本手工扫描请求避免了直接访问输入挂载盘，但其它任务摘要路径仍可把同类阻塞传播到新扫描/取消请求。纯分页 summary 读取不经过该全局锁，不能把它描述为“全部页面必然冻结”。
- **建议**：摘要存储仅用已知事件/缓存；挂载探测移出全局锁，单独限流、可超时/可丢弃；类似已有 `repair_artwork_paths` 的 I/O 外置 + CAS 方案。
- **置信度**：高，受控线程/事件复现锁依赖；未验证真实文件系统最长阻塞时长。

## 已有可靠设计

1. **扫描请求去 I/O**：`submit_scan` 仅词法校验/规范化路径；扫描后台执行，轮询/取消扫描不 stat 挂载盘。相比请求线程递归遍历是明确改进。
2. **扫描事务边界**：整批 `_prepare_tasks` 后，父扫描成功和所有子任务在 `upsert_many([*prepared, task])` 同一事务提交，再入队；取消/提交使用相同条件锁。准备失败/取消会清理临时配置，避免已取消扫描复活。
3. **受限任务执行**：固定全局工作线程数（默认 4，上限 32）及 batch 并发，finally 释放并发占位，主任务不会无界创建线程。
4. **SQLite 基础**：WAL、单事务批量写、独立 task_logs、外键删除、固定 SQL 词汇和绑定参数、created/status 索引；JSON 首次迁移对损坏和重复 ID 失败关闭并先备份。
5. **历史路径修复并发控制**：`repair_artwork_paths` 在数据库事务外做媒体 I/O，再比较旧 payload/summary 更新；并发删除/编辑优先。这一模式值得扩展到普通任务。
6. **分页与轻量轮询**：列表读取预存 summary，避免逐页读全部日志；日志内存/展示分别有 5000/1500 行上限。
7. **分 P 保守处理**：同一批中重复真实路径去重，分 P 合并后保留小尾段，预先检查每一目标，避免明显的同名覆盖；不足主要在执行期事务/恢复。
8. **外部服务基础隔离**：下载快照 single-flight、5 秒缓存、独立 4 线程池；普通网络请求设置超时；删除种子明确 `deleteFiles=false`；媒体同步异常不改变已完成任务状态。

## 非本次确认缺陷的运行边界与补强建议

- 主任务有并发池，但图片重试/封面搜索/每次成功后的媒体同步各起 daemon thread；媒体自动扫描延迟最高一天且每成功影片一条线程。大批量部署需要合并媒体刷新、为辅助操作设置统一限流。本次没有以线程耗尽作为已复现问题计数。
- 定时和下载自动任务仍同步执行 `create_tasks`/挂载扫描；定时器单线程、还有全局运行锁，慢挂载可能影响其它规则。需要在真实 NAS 环境做超时、长尾和服务退出演练。
- 进程内 locks/worker queue 不构成多进程协调；本次结论按默认单 Web 进程运行模式评估，不能据此承诺多个 Uvicorn worker 共享同一 data 目录安全。
- 真正上线前宜补两类集成回归：qB 完成/校验/暂停/移动状态矩阵，以及媒体整理“第二步失败、进程中断、恢复、重复输入”故障矩阵。

## 建议修复顺序

功能修复先处理 T01（未完成媒体进入自动化）、T02（停止意图丢失），再处理 T04/T05 的还原和编辑持久性、T06 的长期去重。T03（归档部分提交）与 T07（慢挂载锁传播）按部署的故障恢复需求并行验收。所有条目保留本次离线复现，再做相应真实集成验证。
