# Web 流畅度体检与优化方案

日期：2026-09-23。本文保留优化前的体检与建议；用户采纳后的实现、复测和升级说明见 [优化实施记录](web-performance-improvements-2026-09-23.md)。

## 结论

最优先的瓶颈是任务历史的整表读取、整表写入，以及手动任务页的全量 DOM 重建。此前的首屏按需加载、任务轮询防重入、概览分页、摘要裁剪和 GZip 都仍在，已有收益，但没有消除历史数据增长带来的开销。

本地 `data/tasks.json` 只有空数组，不能代表实际部署。因此本次用临时数据目录构造 100 / 1,000 / 5,000 条完成任务，每条保留 40 条进度事件。没有修改真实任务、预设或影片，没有访问外部爬虫、下载器或媒体服务器。

## 实测范围与结果

环境：Windows 11，Python 3.12.7。每项通常执行 3 次，表中为中位数；24 次封面查找是一次串行批次。HTTP 使用 FastAPI TestClient 在进程内执行，认证依赖被替换为测试用户，任务摘要已预热。

| 指标 | 100 条 | 1,000 条 | 5,000 条 |
| --- | ---: | ---: | ---: |
| 任务 JSON 文件大小 | 0.77 MB | 7.65 MB | 38.27 MB |
| 读取并解析任务 JSON | 3.20 ms | 34.66 ms | 202.86 ms |
| 生成已缓存任务摘要列表 | 3.37 ms | 36.03 ms | 208.52 ms |
| `/api/tasks`，不压缩 | 7.25 ms | 42.69 ms | 231.26 ms |
| `/api/tasks`，GZip | 8.32 ms | 52.85 ms | 266.91 ms |
| 任务响应解压后大小 | 0.109 MB | 1.092 MB | 5.460 MB |
| 查询单个任务详情 | 3.85 ms | 34.62 ms | 206.98 ms |
| 24 次封面路径查找合计 | 85.49 ms | 790.16 ms | 4,391.92 ms |
| 保存一个任务 | 17.09 ms | 118.28 ms | 1,756.85 ms |

封面这一项仅计算后端路径查找，不包括图片传输、解码、浏览器绘制；也不是宣称页面一定要等 4.39 秒。它说明展示一页封面会放大整表读取的成本。保存任务时持有共享任务锁，这段时间会阻塞同样需要该锁的列表/详情操作，因此“平时还行，刮削时卡顿”有明确的代码原因。

日志处理另做了隔离测试：模拟每收到一条事件就重新清理并解析此前全部事件。100 / 500 / 1,000 条事件的累计耗时分别为 26 / 644 / 2,614 ms，符合重复扫描带来的近似二次增长。该测试没有加入磁盘保存；真实高并发还会叠加锁和写盘开销。

当前静态资源大小：`app.js` 214,288 B，`app.css` 40,373 B，`overrides.css` 41,107 B。三者 GZip 估算合计约 67.6 KB，实际响应均带 `Cache-Control: no-store`。压缩已经开启，继续压缩脚本并不是第一优先级；有效缓存能减少重复访问成本。

这些数据不包含公网/TLS/反向代理、NAS 挂载、真实图片分辨率、浏览器布局、INP/LCP 或移动设备。模拟内容重复度高，JSON 文件中的压缩大小估算不能代表真实线上压缩比；也不能将本地 API 耗时直接当作线上首屏耗时。

## 按优先级的检查发现

| 优先级 | 范围与代码依据 | 影响 | 优化方案 |
| --- | --- | --- | --- |
| P0 | `storage.py:load_tasks/save_tasks`、`tasks.py:_persist` | 每次查询读全表，每次更新重写所有任务及日志；保存期间占用共享任务锁 | 迁移到 SQLite，任务摘要、任务详情、事件分表；按 ID 更新；本地数据库使用 WAL 和短事务。JSON 保留为兼容导入/导出格式，迁移前备份并校验记录数 |
| P0 | `tasks.py:get_cover_path/get_fanart_path` | 每张图片重新读取全部任务并解析该任务日志；NAS 路径探测进一步放大等待 | 按任务 ID 直接查持久化输出路径，封面请求不解析日志；生成固定尺寸缩略图；图片替换时更新版本，使用私有缓存和条件请求 |
| P0 | `app.js:renderTasks`（最后一个定义） | 手动任务列表无分页，隐藏的卡片内容也被创建；筛选每次输入立即遍历和重建 | 增加服务端分页/筛选，默认 50 条；输入去抖约 200 ms；任务按 ID 局部更新；展开时再生成重内容，超大队列再考虑虚拟列表 |
| P1 | `server.py:tasks`、`tasks.py:list_task_summaries` | 概览虽然每页只展示少量卡片，仍传输全部历史；5,000 条解压后约 5.46 MB | 拆分统计、活动任务、历史页接口；服务端做概览分组和排序；轮询版本号/增量，未变化返回 304，避免每 5 秒重新序列化全部历史 |
| P1 | `app.js:loadTasks` 与末尾 `setInterval` | 后台标签页仍请求；设置页也轮询全部任务；任务请求虽有防重入，但下载、定时任务接口没有同等保护 | 页面不可见时暂停，恢复时立即补拉；按当前页面订阅；用请求完成后的 `setTimeout` 调度；统一超时、取消、失败退避与防重入 |
| P1 | `app.js:api`、初始化 IIFE | fetch 没有超时；如果任务接口悬挂，`tasksLoading` 一直为 true；恢复“设置”等页面也先等待任务列表 | `AbortController` 设置可配置超时；首屏认证后立即显示目标页面骨架，只加载该页必要数据；错误明确显示重试入口 |
| P1 | `app.js:openTaskDetail`、`loadTasks` | 每轮刷新详情先清空为“正在读取”，再重建整个详情和图片；选择文字时虽有保护，普通浏览仍会闪烁 | 初次打开显示骨架，后续仅更新变化字段与日志；保留图片、滚动和焦点；详情请求增加防重入及请求序号，丢弃过期响应 |
| P1 | `tasks.py:_run_task/_task_progress/_clean_log_lines` | 每条事件重复扫描整个日志尾部；每 20 条或资源事件触发整表落盘 | 收到结构化事件时增量维护进度；日志追加写入独立存储；普通进度按 0.5～1 秒合并保存，结束/错误立即保存 |
| P1 | `tasks.py:create_task/_run_task` | 每个任务先启动一个线程，再等待批次配额；限制按 batch 而非全局，多批次可累加进程数 | 有界全局工作队列，固定 worker 数；同时限制全局与批次并发。保留取消、恢复和批次公平性 |
| P1 | `tasks.py:create_tasks/create_task/_build_task_config` | 批量创建同步执行；每个文件反复读取/验证预设并单独保存，数量增多会拖慢创建接口 | 每批次固定配置快照，配置校验一次，批量插入任务；大型目录扫描变为后台作业并返回扫描进度 |
| P1 | `server.py:downloads`、`qbittorrent.py` | 每轮串行访问所有下载器；登录及列表分别可能等 8/10 秒；GET 路径还可能执行自动清理 | 后台按下载器刷新快照，HTTP 读取缓存并返回更新时间；只刷新可见下载器或有限并发；自动维护留给后台 worker，避免轮询叠加副作用 |
| P1 | `server.py:disable_asset_cache` | JS/CSS 即使带版本号仍禁用缓存，每次刷新重复下载 | 使用内容 hash 版本的资源名和长期 immutable 缓存；HTML 用 no-cache；没有 hash 的资源先用 ETag/no-cache，避免 beta 更新后旧资源残留 |
| P2 | `app.js:showView/loadPresets/loadCrawlerNames/loadPathTools` | 多次切页重复请求静态配置，`loadPathTools` 还会重复检查 GitHub 更新 | 配置按修订号缓存，保存后失效；公共字典一次加载；更新检查设置会话缓存和超时，保持非阻塞 |
| P2 | `server.py:tasks`、定时历史接口 | 每次轮询都遍历定时/下载历史，为旧任务推算来源 | 一次迁移并持久化 source；历史日志分页；不要在热路径不断兼容同一批旧数据 |
| P2 | `tasks.py:recover_interrupted_tasks` 与 `_logs` | 启动时把所有完成任务的日志载入内存，正常完成后也不立即释放；单任务上限无法限制总量 | 内存只留活动任务的环形缓冲，完成详情按需读取；设置缓存容量；诊断日志采用明确的可配置保留策略 |
| P2 | `app.js` 重复函数定义、`overrides.css` 长期叠加 | `taskCard` 3 个定义、`renderTasks` 2 个、`renderOverview` 4 个，最后一个覆盖之前定义，增加维护误判和无用资源 | 清理被覆盖的旧函数与失效样式，按页面拆模块；保留行为回归。此项优先级低于数据库和 DOM 改造 |
| P2 | `server.py` 同步爬虫测试和媒体调用 | 爬虫测试子进程可占用请求线程至 90 秒，多个慢外部请求会争用请求线程池 | 长操作返回 job ID，后台执行并单独限流；前端查询状态。常规轻量 API 保持短请求 |
| P2 | 全链路可观测性 | 目前缺少能够区分服务端、网络、浏览器等待的统一指标 | 加 Server-Timing 和接口耗时/体积/队列长度/锁等待统计；浏览器采样长任务、LCP、INP、请求失败，建立历史规模基准 |

不要直接用“增加 Uvicorn workers”解决上述问题：登录会话、任务进程与调度器状态目前在进程内，模块导入还会启动定时线程。多进程前须共享会话状态并保证调度器单实例，否则可能出现登录不稳定或重复调度。SQLite WAL 方案也应将数据库放在本地持久化磁盘，影片可以继续放 NAS；网络文件系统需另评估数据库部署方式。

## 建议实施顺序与验收

1. **先减少用户可见停顿**：手动任务页分页、按页加载、未变化不重绘、详情局部刷新、隐藏页暂停、统一请求超时、防重入，以及静态资源缓存。检查滚动、选择文字、编辑表单在轮询期间不丢失。
2. **消除历史规模的主要成本**：SQLite 存储及兼容迁移、日志独立存储、封面路径直接查找、缩略图缓存、列表增量 API。先备份，验证迁移前后任务 ID、状态、日志、还原信息一致，再切换；保留回退路径。
3. **控制后台资源竞争**：有界全局 worker、配置快照与批量入库、下载器缓存、事件增量处理、内存与日志保留策略；再考虑 SSE 替换活跃任务轮询。
4. **部署环境验收**：在实际 Docker/NAS 环境分别测试空闲、4 个刮削进程、下载器不可达、10,000 条历史、后台标签页及受限带宽；再测移动浏览器。

建议目标（尚未实现或证明）：10,000 条历史下分页任务 API p95 < 200 ms，单任务状态持久化 p95 < 50 ms；重复打开概览命中资源/缩略图缓存；后台标签页没有周期性列表请求；连续 5 分钟使用中不因轮询出现 > 100 ms 的主线程长任务；真实用户 INP < 200 ms、LCP < 2.5 s。目标需结合真实 NAS、硬件和带宽复核，不能由当前本机数据保证。

## 本次已完成的分 P 修复

- 同目录、同一规范化番号且分片编号唯一的文件合并为一个任务，支持数字、CD/part/pt 后缀、补零和多位编号；FC2 常见写法可以混用。
- 任务配置保存明确的文件清单，工作进程只处理这些文件，不扫描同目录其他影片。识别使用该任务的预设，不修改全局配置。
- 按数字顺序整理并保留原编号，例如 `-1/-2/-10` 输出 `-CD1/-CD2/-CD10`；只剩 `-1` 时仍保留 `-CD1`，不会重置为无分片名称。普通单文件保持原有命名。
- 一个分片达到最小文件大小时，其较小尾片也纳入任务；歧义或重复编号明确报错，避免静默选择某个文件。
- `extrafanart` 目录允许已存在；不自动删除该目录。移动前检查全部目标路径，已有视频不会被覆盖。
- 不同目录中的同番号文件不自动合并；只提交一个文件路径时也只处理这个文件。对旧任务建议升级后重新扫描剩余源目录；旧记录及已整理文件不会自动迁移或改名。

离线回归使用临时影片占位文件和模拟爬虫/图片响应，覆盖任务创建、配置传递、扫描、整理、硬链接、STRM、目标冲突、已有剧照目录。真实网站可用性不在这些回归测试的验证范围内。

