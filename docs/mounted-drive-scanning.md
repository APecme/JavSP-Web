# 挂载盘目录扫描修复与验证

对应 GitHub 议题 #13、PR #14。吸收 PR 的本机多选入口，将目录和所选文件的发现过程放入现有后台任务池，并在应用界面展示扫描状态。

## 原因与实现

原 POST /api/tasks 在返回之前调用 create_tasks，目录模式需要完成递归枚举、文件属性查询和任务配置准备。挂载盘这些操作可能阻塞；原前端创建请求超时为 90 秒。单文件模式不递归枚举，符合议题报告的差异。没有原用户的挂载盘日志，因此“实际失败一定由超时触发”仍未证实。

现在请求线程只做字符串归一化、保存扫描任务和入队，不调用媒体路径的 exists/is_file/stat/resolve。创建返回 HTTP 202，兼容 tasks/count 字段，并增加 scan=true；此时 count 是扫描任务数量，而不是最终影片数量。扫描进度可通过原任务列表及详情接口获取。

后台复用原分 P 分组、大小筛选和任务配置逻辑。显式多选列表只读取所选文件，不递归扫描同级文件；同一次操作的影片任务共用 batch_id，继续遵守预设并发数。短尾片按整部影片判定大小，重复路径去重，歧义分片报错。

全部文件准备成功后，在同一 SQLite 事务中写入影片任务和“扫描完成”记录，再放入执行队列。取消和提交互斥；取消后即使之前阻塞的 I/O 恢复，也不再提交子任务或重建已删除的扫描记录。未提交的扫描在服务重启后重新排队，已经完成的扫描不会再次展开。

本机多选接口保留登录校验，共用带互斥保护的文件对话框逻辑，并在异常时清理窗口。前端一次 POST 提交整个列表，提交期间防止重复点击，并区分扫描进度与影片刮削进度。

## 验证

Python 3.12 下执行全部 unittest：76 项通过，其中新增 12 项扫描回归测试。

- 在模拟的目录枚举被事件持续阻塞时，真实 FastAPI 创建接口已返回 202；详情查询仍可正常完成。
- 对媒体路径 stat 设置失败断言，验证提交、轮询和取消都不触碰该挂载路径。
- 阻塞中取消并删除扫描，再释放 I/O，验证没有子任务入队，也不恢复已删除记录。
- 验证多选分 P、小尾片、重复路径、同批并发、单文件、空目录、失效路径、网络断开、歧义分片、提交前取消和重启恢复。
- 原有分 P、任务存储、应用更新等回归一并通过。
- 两组 Node 检查通过：原前端请求/版本/更新遮罩测试，以及新增的批量提交、修改路径、重复点击、错误重试、多选入口与最终任务卡片渲染测试。

可复现命令（在项目根目录，已安装 requirements.txt 和 tests/requirements.txt）：

    python -m unittest discover -s tests -v
    node tests/test_web_client.cjs
    node tests/test_scan_client.cjs

运行测试时建议将 JAVSP_WEB_DATA_DIR 指向临时目录。本次使用 tmp/scan-tests-data，测试媒体为临时目录中的合成文件，没有启动真实影片抓取。

## 实测边界

未连接原用户的 CloudDrive2/115 挂载盘，也没有实测原生 tkinter 对话框；对话框采用测试替身验证返回值、错误路径和资源清理。真实挂载盘仍需要补一次目录、多选与取消的现场验证。

取消不能强行打断操作系统中已经阻塞的文件系统调用；页面会立即显示取消，后台在该调用返回后检查取消标志。工作线程数量仍受全局上限控制。
